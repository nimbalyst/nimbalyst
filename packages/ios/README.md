# Nimbalyst for iOS

Native SwiftUI companion app for [Nimbalyst](https://nimbalyst.com), the AI-native code editor. View and interact with your AI coding sessions on iPhone and iPad, synced in real-time from your Mac.

## Features

- **Real-time session sync** - Sessions appear on your phone as they're created on desktop
- **End-to-end encryption** - All data encrypted with AES-256-GCM; the server never sees plaintext
- **Rich transcript viewer** - Full chat transcripts with code blocks, tool calls, and interactive widgets
- **Session management** - Search sessions, group by time period, create new sessions from mobile
- **iPad split view** - Sidebar navigation on iPad, stack navigation on iPhone
- **Desktop presence** - See when your Mac is online and connected
- **Session fleet Live Activity** - Lock Screen card and Dynamic Island showing what your fleet is doing, mirroring the macOS menu bar strip; tap a row to open that session

## Getting Started

### Prerequisites

- macOS with Xcode 16+
- Node.js 20+
- [XcodeGen](https://github.com/yonaskolb/XcodeGen) (`brew install xcodegen`)

### Setup

1. Clone the monorepo and install dependencies:
   ```bash
   git clone https://github.com/nimbalyst/nimbalyst.git
   cd nimbalyst
   npm install
   ```

2. Build the transcript web bundle:
   ```bash
   npm run ios:build:transcript
   ```

3. Generate and open the Xcode project:
   ```bash
   cd packages/ios/NimbalystApp
   xcodegen generate
   open NimbalystApp.xcodeproj
   ```

4. Select a simulator or device and press Run.

### Pairing with Desktop

1. On your Mac, open Nimbalyst and go to **Settings > Session Sync**
2. Enable sync and click **Pair Mobile Device**
3. On the iOS app, scan the QR code
4. Sign in with the same Google account you use on desktop

The QR code contains the server URL and encryption seed. The encryption key is derived locally and never sent to the server.

## Architecture

```
NimbalystNative/     Swift Package with all business logic
  App/               AppState, navigation, lifecycle
  Auth/              Stytch OAuth (Google sign-in)
  Crypto/            AES-256-GCM, PBKDF2 key derivation
  Database/          GRDB (SQLite) with reactive ValueObservation
  LiveActivity/      Fleet Live Activity attributes, formatting, token lifecycle
  Models/            Project, Session, Message, QueuedPrompt
  Sync/              WebSocket sync with CollabV3 server
  Views/             SwiftUI views + WKWebView transcript

NimbalystApp/        Xcode app target (generated by XcodeGen)
  NimbalystWidgets/  Widget extension: Live Activity lock screen + Dynamic Island
src/transcript/      React web bundle for chat transcript (WKWebView)
```

The app connects to the same [CollabV3](../collabv3/) sync server as the desktop app. Session data flows:

```
Desktop (Electron) -> CollabV3 (Cloudflare DO) -> iOS (WebSocket)
```

All data is encrypted client-side before transmission. The server stores only opaque encrypted blobs.

### Session Fleet Live Activity

The Lock Screen card and Dynamic Island render the same derived fleet snapshot as the macOS menu bar strip, so the two surfaces cannot disagree. The card is **entirely server-started** — the app never calls `Activity.request`:

```
Desktop TrayManager -> fleetActivityUpdate (WebSocket) -> IndexRoom -> APNs -> phone
```

- The app registers two ActivityKit tokens with the server and does nothing else. A **push-to-start** token belongs to the app and lets the card appear on a phone whose owner has not opened it today; an **update** token belongs to one running activity and dies with it. They are never interchangeable — sending an update to a push-to-start token fails at APNs with an error that reads exactly like a bad token.
- When an activity ends (including at ActivityKit's ~8-hour ceiling), `FleetActivityController` drops its update token and the server starts a fresh card on the next snapshot.
- The desktop coalesces on transitions and sends a heartbeat every 5 minutes, inside the card's 12-minute stale window. A card that outlives its stale date dims rather than showing a count that stopped being true.
- Rows rank by what to deal with first, which is deliberately *not* the menu bar's announcement urgency — a crashed session is dead rather than blocking, so failures rank below anything actually waiting.
- Tapping a row opens `nimbalyst://session/<id>`, the same route a notification tap uses.
- Settings > **Session Fleet Live Activity** turns it off; the toggle is independent of push notification permission, since a Live Activity needs none.
- **The phone card stays visible while you use the Mac.** Mac presence and fleet-strip visibility do not suppress it. macOS mirroring may also show the card alongside the desktop strip. Each phone or tablet has its own delivery lifecycle; expired update tokens are retired so the next eligible fleet snapshot can start a replacement.

**Live Activity content is not end-to-end encrypted.** APNs has to hand the payload to the system for rendering, so the session titles on the card travel in plaintext — the same exposure the existing push notification titles already have. Everything on the normal sync path stays encrypted.

### Project Structure

| Directory | Description |
|-----------|-------------|
| `NimbalystNative/` | Swift Package with all app code (SPM) |
| `NimbalystApp/` | Xcode app target with `project.yml` (XcodeGen) |
| `NimbalystApp/NimbalystWidgets/` | Widget extension (`com.nimbalyst.app.widgets`), embedded in the app |
| `CryptoCompatibility/` | CommonCrypto bridging for PBKDF2 |
| `src/transcript/` | React transcript loaded in WKWebView |

### Widget Extension

The Live Activity only exists if `NimbalystWidgets.appex` ships inside the app bundle, so the app target depends on it in `project.yml` and Xcode embeds it into `PlugIns/`.

The extension **does not link `NimbalystNative`.** It shares `FleetActivityAttributes.swift`, `FleetActivityFormatting.swift`, and `NimbalystColors.swift` by target membership instead. The package pulls in GRDB and PostHog, and a widget extension runs under a tight memory limit with no business paying for a database engine it will never open. Sharing the source files is also what Apple's own samples do for `ActivityAttributes`: ActivityKit matches an activity to its attributes by the *unqualified* type name, so both targets compiling the same declaration is exactly what is required.

Two consequences worth knowing before you edit either target:

- **The extension's `CFBundleShortVersionString` / `CFBundleVersion` must match the app's.** App Store Connect rejects an embedded extension whose version drifts. `scripts/ios-release.sh` bumps both plists.
- **Renaming `FleetActivityAttributes` breaks push-to-start silently.** The server sends the type name as a string (`LIVE_ACTIVITY_ATTRIBUTES_TYPE` in `collabv3/src/liveActivity.ts`); APNs rejects a start whose `attributes-type` does not name a real conformer in the app.

### Transcript Web Bundle

The chat transcript is rendered by the same React components used in the desktop app, bundled as a standalone IIFE with Vite. The font (Material Symbols) is bundled locally since WKWebView loads from `file://`.

The Xcode pre-build script automatically builds and copies the transcript when you build in Xcode.

## App Store Compliance

### Capabilities and Signing

| Requirement | Where |
|-------------|-------|
| `NSSupportsLiveActivities` | `NimbalystApp/Sources/Info.plist` |
| `aps-environment: production` | `Sources/NimbalystApp.entitlements`, generated from `project.yml` |
| App ID for `com.nimbalyst.app.widgets` | Created by Xcode automatic signing; `xcodebuild` in CI needs `-allowProvisioningUpdates` |

**A Debug build cannot receive pushes from the production sync worker.** The entitlements file says `production` in every configuration, but at install time the *provisioning profile* governs. Verified by inspecting a local archive: `codesign -d --entitlements` reported `aps-environment: development` and `get-task-allow: true` despite `project.yml` asking for `production`. Tokens from such a build come back `400 {"reason":"BadDeviceToken"}` from `api.push.apple.com`.

The `environment` field on `RegisterLiveActivityTokenMessage` exists for exactly this and is deliberately wired on neither end — iOS hardcodes `"production"`, and the server neither stores nor reads it. Push testing goes through TestFlight or a Release-signed build (NIM-4751); we do not use the APNs sandbox anywhere.

**Installing TestFlight *over* a Debug build is not enough — delete the app first.** ActivityKit keeps vending the push-to-start token from the old provisioning, so `pushToStartTokenUpdates` hands back a dead sandbox token indefinitely and the server sees `BadDeviceToken` forever. A full delete is what forces a fresh token. This cost a long debugging session on 2026-08-30; the giveaway was the token prefix being byte-identical across both builds.

### Encryption Export (ITSAppUsesNonExemptEncryption)

The app uses AES-256-GCM encryption (via CryptoKit) for end-to-end encryption of synced data. `ITSAppUsesNonExemptEncryption` is set to `false` in Info.plist because:

1. The encryption uses Apple's built-in CryptoKit framework, not a custom implementation
2. It is used solely for protecting the user's own personal data in transit between their devices
3. It is not used for direct communication between third parties
4. HTTPS/TLS (handled by the OS) is used for all network communication

This qualifies as exempt under US BIS encryption export regulations (Category 5, Part 2, Note 4).

### Privacy Manifest (PrivacyInfo.xcprivacy)

The app declares:
- **UserDefaults** access (reason CA92.1: app-specific preferences)
- **Product interaction** data collection (PostHog analytics, linked to identity)
- **No tracking** (analytics are not used for cross-app advertising)
