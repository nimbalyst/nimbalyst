# Cloudflare sandbox management

This package supplies a private management Worker deployed into the user's Cloudflare account. Nimbalyst's Settings panel uses their local Wrangler named SSO profile and requires an explicit account choice. The application does not request or store Cloudflare API keys. Local end-to-end tests run on the host; Docker is used only to build and smoke-test the headless Linux image.

The Worker manages one sandbox per installation: review a deployment, deploy, observe status, wake, stop, and delete. Deployment success and container readiness are separate observations. Idle sleep is five minutes, with at most one `standard-3` instance. Files and processes inside the sandbox remain ephemeral; container stop and idle sleep lose them.

The private RPCs `provision({ files, allowedHosts })`, `startNode({ configPath })`, `nodeStatus()`, and `stopNode({ discardEphemeralData: true })` provision files beneath `/home/nimbalyst/`, start the headless node with `serve --config`, observe its process and the last approximately 4 KiB of logs, and send SIGTERM. Provisioning rejects traversal and symbolic links, limits total UTF-8 file content to 256 KiB, and defaults file permissions to `0600`. A running node keeps the container alive. Status does not wake an idle container. Stop retains the process record if the node is still running after a brief wait, allowing observation or another stop attempt.

General internet access stays disabled (`enableInternet = false`). Provisioning unions concrete DNS hosts with `github.com`, `api.anthropic.com`, `platform.claude.com`, `console.anthropic.com`, and `sync.nimbalyst.com`. The pinned Containers SDK supports `*` glob patterns, but this RPC accepts concrete hosts only. Files and process records do not provide durable node storage or prove successful personal-sync enrollment.

HTTPS interception is explicit on this preview SDK. The initial empty host allowlist enables certificate injection while denying all destinations until provisioning. The outbound response handler removes `Upgrade` and `Connection` from successful WebSocket responses so the interception runtime emits each header once; forwarding both copies makes Node reject the handshake. Other HTTP responses and WebSocket negotiation headers pass through unchanged, and the SDK applies the host allowlist before this handler.

Paired sandbox sessions appear in the desktop's normal session list for the requesting workspace. Opening one subscribes to its encrypted session room and renders the existing canonical transcript format. Follow-up prompts and stop requests go to the remote host. These mirrors never create executable local session rows or mount local tool controls. At most four remote transcripts are observed at once, with an 8 MiB content limit per view; closing the last view releases its connection and memory. Account changes clear those views. After the headless process restarts, older sessions remain readable but their follow-up and stop controls are disabled; start a new session because the sandbox does not restore prior execution state. Large tool output may already be truncated by the sync protocol, and interactive tool answers are not supported by this initial remote view.

Provisioning validates up to 32 files and 16 requested hosts before changing files or egress, creates each destination with mode `0600` before writing content, and unlinks it if writing or the final chmod fails. Observing a node that exited releases keep-alive and clears its process record while returning that observation's exit code and recent logs. Path checks and writes are separate operations, so an unprivileged container process can still race them by changing a symlink between the check and write.

## Deployment artifacts

The Worker and container base are pinned to Sandbox `0.13.0-next.751.1`. Preview `exec(argv)` returns a process handle when execution starts; smoke checks and file commands await its output before proceeding. Node launches use argv directly, and persisted launch intent includes the config path and start time so observations can reject stale process IDs or recover an interrupted launch. Process lookup and log observation do not start an idle container.

Inside the Sandbox subclass, the installed SDK's `exec` returns an RPC descriptor. The exported `createExtensionProcessSandbox` adapter normalizes it to a handle; its installed type explicitly documents this purpose. The preview extensions surface is experimental, so this adapter is tied to the exact SDK pin.

Stable and preview control protocols are incompatible. Desktop deployment uses `--containers-rollout immediate`; Wrangler 4.125.0 accepts this option in both help and a local dry run. Existing service bindings and container configuration remain unchanged. During migration, the published image digest in `release.json` must be replaced with the newly published preview-based Nimbalyst image before live deployment; local artifact checks validate the pinned base SDK line, not the contents of that published image.

Install this isolated package with `npm ci --prefix packages/cloudflare-sandbox --workspaces=false --ignore-scripts`, then run `npm run build --prefix packages/cloudflare-sandbox`. Electron packaging performs both steps automatically. The generated `dist/worker.mjs` bundles the pinned Sandbox SDK; `dist/manifest.json` binds its SHA-256 to the release image. No project directory or dependency installation is sent to Cloudflare by the desktop flow.

`release.json` pins the published Nimbalyst Linux image by immutable `docker.io/<organization>/<repository>@sha256:<digest>` reference. Keep its Sandbox SDK version aligned with the image and rebuild after an approved image publication. A release with `image: null` remains buildable for local validation but cannot be deployed. Never substitute the upstream Sandbox base image: it does not contain the Nimbalyst headless runner. Building an image locally is not publication or Cloudflare acceptance.

Cloudflare supports registry image deployment without a local Docker daemon. See [Cloudflare container deployment](https://developers.cloudflare.com/containers/guides/deploy/) and [Sandbox deployment](https://developers.cloudflare.com/sandbox/guides/deploy/). Wrangler deploys the Worker before processing container configuration, so failures can leave partial resources. The desktop must preserve their identity for recovery and deletion.

The deployment config uses an explicit account ID, disables `workers.dev` and preview URLs, and exposes the named `SandboxManager` entrypoint only over a service binding. Its HTTP handler returns 404. A private deployment intentionally has no public URL. Management calls must run through the selected Wrangler profile's owned directory binding and explicit account configuration; a CLI profile flag alone is insufficient for Wrangler's remote binding authentication.

## Local validation

Run `npm run typecheck --prefix packages/cloudflare-sandbox`, `npm run test:artifact --prefix packages/cloudflare-sandbox`, and the focused Worker tests from the repository Vitest runner. The artifact check compiles the actual Worker, verifies its exported entrypoints and bundled dependencies, and confirms deterministic bytes and manifest hashes. Linux image build and smoke instructions are in [container/README.md](container/README.md). None of these checks proves a live Cloudflare deployment.
